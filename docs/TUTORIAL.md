# Настройка маршрута по шагам

**[English](TUTORIAL.en.md)** · Русский

Два условных примера. Названия организаций, групп и категорий вымышленные —
подставьте свои.

- **Пример 1** — «Запрос с согласованием»: согласование руководителя →
  исполнение отделом → итог заявителю. Новый порядок исходов: отказ,
  возврат на уточнение, итог решением заявки.
- **Пример 2** — «Работа внутри отдела»: три задачи в одной заявке, прежний
  порядок. Самая простая настройка.

Перед началом — [установка](INSTALL.md) и право **«Маршруты этапов»** в своём
профиле ([RIGHTS.md](RIGHTS.md)).

---

## Пример 1. Запрос с согласованием

| № | Этап | Режим | Кто делает | Отказ | Возврат на уточнение |
|---|---|---|---|---|---|
| 10 | Согласование руководителя | Согласование | указывается при прохождении | прервать | к этапу 10 |
| 20 | Исполнение отделом | Дочерняя заявка | группа «Отдел исполнения» | прервать | к этапу 10 или 20 |
| 30 | Итог заявителю | Задача в заявке | группа «Первая линия» | остановить | — |

### Шаг 1. Справочники GLPI

Маршрут опирается на штатные справочники — подготовьте их первыми.

**Организации.** Для примера: корневая организация, в ней заявители,
и подчинённая организация «Отдел исполнения» — туда уйдёт дочерняя заявка.

**Группы** (**Администрирование → Группы**):

| Группа | Где | Признаки |
|---|---|---|
| Первая линия | корневая организация, **видна в подчинённых** | «Может быть назначена заявке» |
| Отдел исполнения | организация «Отдел исполнения» | «Может быть назначена заявке» |

Без признака «Может быть назначена заявке» группы нет в списке этапа. Группа
этапа «Задача в заявке» должна быть видна в организации заявки — отсюда
«видна в подчинённых». Включите людей в группы (вкладка «Пользователи»).

**Категории** (**Настройки → Списки → Категории заявок**), обе видимые
в подчинённых организациях:

1. «Запрос с согласованием» — по ней правило запустит маршрут.
2. «Этап маршрута» — служебная, для дочерних заявок этапов.

**Профили.** Каждому участнику нужен профиль технического специалиста в той
организации, где лежит его объект: согласующему и первой линии — в организации
заявки, исполнителю отдела — в «Отделе исполнения». Профиль самообслуживания
позволяет отвечать на визы и отзывать свою заявку, но не работать с этапами.

**Календарь и SLA** — по желанию: календарь для срока этапа, SLA для
дочерней заявки.

### Шаг 2. Маршрут

**Администрирование → Маршруты этапов → Добавить**

| Поле | Значение | Зачем |
|---|---|---|
| Название маршрута | Запрос с согласованием | видят исполнители и заявитель |
| Тип объекта | Заявка | после первых запусков не меняйте |
| Организация | корневая | |
| Виден в подчинённых единицах | **Да** | иначе правило в подчинённой организации не увидит маршрут |
| Режим контроля | Журнал | начните с журнала, позже — «Предупреждение», затем «Запрет» |
| Запрещать решение до прохождения маршрута | Да | иначе маршрут лишь подсказка |
| Писать ход этапов в ленту заявки | Да | заявитель видит ход; нужен, чтобы отчёт этапа 30 попал в итог |
| Показывать вкладку маршрута инициатору | Да | |
| Инициатор может отозвать заявку | Да | |
| Рабочий календарь | по желанию | для «Срока этапа» |
| Обработка исходов отделов | пока **Прежний порядок** | новый включим в шаге 4 |
| Маршрут активен | Да | неактивный правило назначит, но не запустит |

Сохраните.

### Шаг 3. Этапы

Вкладка **«Этапы»** → «Добавить этап». Блок **«Исход отдела и новая попытка»**
внизу формы действует только в новом порядке, но заполнить его можно сразу.

**Этап 10 — Согласование руководителя**

| Поле | Значение |
|---|---|
| Название этапа | Согласование руководителя |
| Порядок | 10 |
| Режим исполнения | Согласование |
| Статус объекта на этапе | Согласование |
| Кто согласует | Указывается при прохождении этапа |
| Порог согласования, % | 100 |
| Инструкция исполнителю | что согласующему проверить |
| Отрицательный исход | Прервать после отказа |

Группу и сотрудника не заполняйте: согласующего укажет исполнитель заявки.

**Этап 20 — Исполнение отделом**

| Поле | Значение |
|---|---|
| Название этапа | Исполнение отделом |
| Порядок | 20 |
| Режим исполнения | Дочерняя заявка |
| Группа-ответственный | Отдел исполнения |
| Статус объекта на этапе | Ожидание |
| Где исполняется этап | Заданная сущность → «Отдел исполнения» |
| Категория дочерней заявки | Этап маршрута |
| SLA дочерней заявки | по желанию |
| Инструкция исполнителю | что сделать и что написать в результате |
| Источник исхода | Явный ответ назначенного исполнителя |
| Отрицательный исход | Прервать после отказа |

**Этап 30 — Итог заявителю**

| Поле | Значение |
|---|---|
| Название этапа | Итог заявителю |
| Порядок | 30 |
| Режим исполнения | Задача в заявке |
| Группа-ответственный | Первая линия |
| Где исполняется этап | Сущность родительской заявки |
| Отчёт о выполнении | Запрашивать, заполнение обязательно |
| Инструкция исполнителю | сформулировать ответ заявителю |
| Отрицательный исход | Остановить после отказа |

«Отрицательный исход» в новом порядке обязателен у каждого этапа, даже если
отказа на нём не бывает.

**Точки возврата.** Этап можно выбрать точкой возврата только после его первого
сохранения. Откройте этап 10 и в «Допустимые точки возврата» выберите
«Согласование руководителя»; откройте этап 20 и выберите оба этапа 10 и 20.
У этапа 30 точек возврата нет — с задачи в заявке вернуть нельзя.

![Форма этапа (снимок версии 1.6–1.7, вымышленные данные; блок «Исход отдела и новая попытка» не виден)](img/ui-stage-form.png)

### Шаг 4. Новый порядок исходов

Откройте маршрут и выберите **«Обработка исходов отделов → Явные исходы
и новые попытки»**. Если у какого-то этапа не хватает источника исхода,
отрицательного исхода или точки возврата недопустимы, маршрут не сохранится
и подскажет, что заполнить.

Новый порядок действует на запуски после сохранения. Уже идущие заявки
доходят по прежнему.

### Шаг 5. Запуск правилом

**Администрирование → Правила → Бизнес-правила для заявок → Добавить**

- **Критерий:** Категория — равно — «Запрос с согласованием».
- **Действия:**
  - Запустить маршрут этапов — назначить — «Запрос с согласованием»;
  - назначить заявке группу исполнителей «Первая линия» — штатным действием
    того же или другого правила. У заявки должен быть исполнитель: он укажет
    согласующего и продолжит маршрут после уточнения.

![Запуск маршрута](img/start-chain.svg)

Если список маршрутов в действии правила пуст — маршрут лежит в другой
организации и не помечен «Виден в подчинённых единицах». Учитывайте порядок
правил и «Остановить обработку»: правило выше может перехватить заявку.

Маршрут можно запустить и вручную: вкладка **«Маршрут этапов»** заявки →
выбрать маршрут → «Запустить маршрут» (нужно право «Маршруты этапов»).

**Форма каталога (по желанию).** В **Администрирование → Формы** создайте
форму и в её назначении задайте категорию «Запрос с согласованием» конкретным
значением — заявитель не ошибётся с категорией. В GLPI 11 каталог открывается
по адресу `/ServiceCatalog`, форма — `/Form/Render/<номер формы>`.

### Шаг 6. Проверка

Проходите маршрут под каждым участником, а не под администратором:
под администратором не видно ни ограничений видимости, ни нехватки прав.

**Обычный путь**

1. **Заявитель** создаёт заявку категории «Запрос с согласованием».
   На вкладке «Маршрут этапов»: этап 10 — «Сейчас», «Ждём: исполнитель заявки
   укажет согласующего».
2. **Первая линия** (исполнитель заявки): в строке этапа 10 (или **Ответ →
   Указать согласующего**) выбирает сотрудника и пишет основание в «Почему он».
3. **Согласующий**: в строке этапа «Согласовать или отказать» → «Согласовать»
   (или штатный ответ на визу в ленте). Этап 10 — «Выполнено», открыт этап 20,
   в «Отделе исполнения» появилась дочерняя заявка «[Этап 20, попытка 1] …».
4. **Исполнитель отдела** открывает дочернюю заявку, вкладку маршрута →
   «Отметить результат» → пишет результат → «Выполнено». Дочерняя заявка
   решается тем же текстом, открыт этап 30.
5. **Первая линия**: «Завершить этап» в строке этапа 30 (или **Ответ →
   Завершить этап**), заполняет «Что сделано».
6. Заявка решена: «Заявка выполнена: все этапы маршрута „Запрос
   с согласованием“ пройдены. Итог: …». Заявитель принимает решение
   штатно.

**Отказ.** Согласующий отказывает с комментарием — заявка решается
с текстом «Отказ на этапе „Согласование руководителя“» и причиной.

**Возврат на уточнение.**

1. Исполнитель отдела: «Отметить результат» → пишет, что уточнить →
   «Вернуть на уточнение».
2. Заявитель видит просьбу ответить комментарием и отвечает.
3. Первая линия: «Продолжить после уточнения» → кратко, что уточнено →
   с какого этапа продолжить (10 или 20).
4. Открывается новая попытка; прежний результат — в «Истории этапа».

**Что ещё проверить**

- Решить дочернюю заявку вручную, без исхода, нельзя — GLPI покажет сообщение.
- Пока маршрут не пройден, заявку нельзя решить (в режиме «Журнал» попытка
  пройдёт, но попадёт в «Действия вне порядка этапов»).
- Заявитель может отозвать заявку с причиной — она решается с этой причиной.
- Статус заявки меняется на «Согласование» и «Ожидание» в течение минуты,
  если включено `itilflow_status_sync`.
- **Лист согласования** (кнопка в шапке вкладки) показывает весь ход.

## Пример 2. Работа внутри отдела

Все этапы — задачи в одной заявке, прежний порядок исходов. Подходит для
внутренней процедуры одного подразделения.

| № | Этап | Режим | Группа | Особенности |
|---|---|---|---|---|
| 10 | Разбор заявки | Задача в заявке | Первая линия | отчёт по желанию |
| 20 | Выполнение работ | Задача в заявке | Отдел исполнения | срок этапа 480 минут |
| 30 | Проверка результата | Задача в заявке | Первая линия | **необязательный**, отчёт обязателен |

1. **Группы.** Обе группы видны в организации заявок («видна в подчинённых»
   из вышестоящей организации): задача живёт в самой заявке, и на время этапа
   плагин добавляет группу в её исполнители.
2. **Маршрут.** Как в примере 1, «Обработка исходов отделов» — «Прежний
   порядок», категория и правило — свои.
3. **Этапы.** Режим «Задача в заявке», «Где исполняется этап» — «Сущность
   родительской заявки». У этапа 20 «Срок этапа, минут» = 480 и рабочий
   календарь у маршрута: просрочку отметит `itilflow_deadlines`. У этапа 30
   «Этап необязательный» = Да.
4. **Прохождение.** Исполнитель каждого этапа нажимает «Завершить этап»
   в строке этапа или в **Ответ → Завершить этап**. На этапе 30 есть
   «Пропустить» — причина обязательна и попадает в ленту.
5. **Конец.** После этапа 30 запрет решения снимается, решение заявки
   оформляет исполнитель штатно.

Чтобы перевести такой маршрут на новый порядок, заполните у этапов
«Отрицательный исход» и выберите «Явные исходы и новые попытки»: в конце
заявка будет решаться автоматически с отчётом последнего этапа в итоге.

## Внедрение

1. Месяц в режиме **«Журнал»**: действия вне порядка записываются, полномочия
   проверяются всегда.
2. Разбор журнала: регулярный обход обычно говорит о регламенте — лишний
   этап, не тот ответственный, нереальный срок.
3. **«Предупреждение»** на переходный период.
4. **«Запрет»**, когда обходов почти не осталось.

Существенно изменённый процесс оформляйте новым маршрутом, а прежний
не удаляйте, пока по нему идут заявки.

Ошибки и их причины — [FAQ.md](FAQ.md).
