# Установка и обновление

**[English](INSTALL.en.md)** · Русский

## Требования

| Что | Требование |
|---|---|
| GLPI | 11.0.x. Объявлено 11.0.0–11.99.99; выпуск 1.9.0 проверен на 11.0.8 |
| База | MariaDB (проверено) или MySQL 8 (не проверялся); таблицы InnoDB |
| PHP | версия, которую требует установленная GLPI 11 |
| Cron | системный запуск `front/cron.php` раз в минуту: задачи плагина работают в режиме CLI |
| Прочее | ничего: без composer, npm и внешних сервисов |

## Установка

### 1. Файлы

Каталог плагина должен называться `itilflow` и лежать в каталоге `plugins/`
вашей GLPI.

Из архива выпуска:

```bash
tar -xzf itilflow-1.9.0.tar.gz -C /var/www/glpi/plugins/
chown -R www-data:www-data /var/www/glpi/plugins/itilflow
```

Из репозитория (корень репозитория — это и есть каталог плагина):

```bash
git clone <адрес этого репозитория> /var/www/glpi/plugins/itilflow
cd /var/www/glpi/plugins/itilflow && git checkout v1.9.0
```

Имя веб-пользователя (`www-data`) и путь к GLPI подставьте свои — как у
остальных каталогов в `plugins/`.

**Архив собирайте на Linux.** Zip, собранный на Windows, не несёт unix-прав:
после распаковки у каталогов может не оказаться бита `x`, и GLPI отдаёт 404
на файлы плагина. Надёжный способ:

```bash
git archive --prefix=itilflow/ -o itilflow-1.9.0.tar.gz v1.9.0
```

### 2. Установка и включение

Из каталога GLPI, от веб-пользователя:

```bash
php bin/console plugin:install itilflow --username=<администратор GLPI>
php bin/console plugin:activate itilflow
php bin/console cache:clear
```

То же можно сделать в интерфейсе: **Настройки → Плагины** → «Установить»,
затем «Включить». Очистку кэша не пропускайте: без неё GLPI может показывать
старые шаблоны. То же — после каждой замены файлов плагина.

Почему так. В рабочем режиме GLPI 11 не перечитывает изменённые шаблоны:
скомпилированная копия ищется по пути файла, а не по его содержимому, и
«Обновить» в списке плагинов её не трогает. С 1.9.0 установка и «Обновить»
сами удаляют скомпилированные копии шаблонов плагина. Но `cache:clear`
по-прежнему нужен: если консоль и веб-сервер работают на разных версиях PHP,
копии веб-сервера из консоли не найти. Сбой этого шага установку
не прерывает — причина пишется в `files/_log/itilflow.log`.

Если на сервере OPcache настроен без проверки времени файлов
(`opcache.validate_timestamps=0`), после замены файлов сбросьте и его:
**Настройки → Общие → Производительность** → «Сбросить», или перезапустите
веб-сервер. Иначе останутся старые классы плагина.

Установка создаёт таблицы, проверяет их схему и при расхождении
останавливается с сообщением. Неполная схема — повод разобраться, а не
продолжать.

### 3. Автоматические действия

**Настройки → Автоматические действия**:

| Действие | Что делает | После установки |
|---|---|---|
| `itilflow_deadlines` | раз в 15 минут отмечает просроченные этапы | включено, режим CLI |
| `itilflow_status_sync` | раз в минуту ставит заявке статус, заданный этапу, в маршрутах нового порядка | **выключено** — включите сами: состояние «Запланировано», режим CLI |

Обе задачи работают только при системном cron:

```cron
* * * * * www-data php /var/www/glpi/front/cron.php
```

Пока `itilflow_status_sync` выключена, в списке маршрутов висит предупреждение
для администратора, а статус заявки по этапам нового порядка не меняется.

### 4. Права

После установки в профилях появляются два права:
**«Маршруты этапов»** и **«Обход маршрута»**. GLPI выдаёт «Маршруты этапов»
профилям с правом изменения настроек и пишет в журнал миграции файл вида
`warning_during_migration_to_1.8.0.log` с напоминанием «review ACLs after
update» — это ожидаемо. Проверьте, у кого право оказалось, и выдайте его
тем, кто настраивает процессы. «Обход маршрута» по умолчанию не выдано никому.

Подробно — [RIGHTS.md](RIGHTS.md).

### 5. Проверка

- `php bin/console plugin:list` — itilflow 1.9.0 в состоянии «Включен».
- В базе девять таблиц `glpi_plugin_itilflow_*`: processes, stages, instances,
  steps, violations, attempts, outcomes, outcomevalidations, commandreceipts.
- В `files/_log/php-errors.log` нет ошибок со словом `itilflow`.
- В меню **Администрирование** есть пункт **«Маршруты этапов»** (нужно право).

## Обновление с 1.8.x

Схема базы в 1.9.0 не меняется: ни таблиц, ни колонок, ни правки строк при
установке. Меняются экраны настроек маршрута и этапа.

1. **Резервная копия** каталога `plugins/itilflow` (и, как всегда, базы).
2. **Файлы.** Замените содержимое `plugins/itilflow` файлами 1.9.0.
3. **Установка** — как выше: `plugin:install`, `plugin:activate`,
   `cache:clear`. Пока `plugin:install` не выполнен, GLPI держит плагин
   выключенным («требует обновления»).

Что увидят администраторы процессов:

- формы маршрута и этапа показывают только нужное, редкое — в свёрнутом
  «Дополнительно»; срок этапа — в рабочих днях или часах;
- строка готовности на маршруте и над таблицей этапов;
- новый маршрут из формы сразу в новом порядке исходов; у маршрутов прежнего
  порядка — плашка и кнопка «Перевести на новый порядок». Существующие
  маршруты сами не меняются: перевод — только по нажатию;
- маршрут, созданный через API без `outcome_contract`, по умолчанию остаётся
  в прежнем порядке.

**Откат** — вернуть файлы 1.8.x и выполнить `cache:clear`: данных, которых
1.8 не поймёт, 1.9.0 не пишет. Маршруты, переведённые кнопкой, останутся
в новом порядке — его понимает и 1.8.

## Обновление с 1.7.x

### Порядок

1. **Резервная копия.** Полный дамп базы и копия каталога `plugins/itilflow`.
   Лучше сначала прогнать обновление на копии рабочей базы.
2. **Файлы.** Замените содержимое `plugins/itilflow` файлами 1.9.0 (старые
   файлы удалите: с 1.8.0 часть шаблонов убрана, часть классов добавлена).
3. **Миграция.**

   ```bash
   php bin/console plugin:install itilflow --username=<администратор GLPI>
   php bin/console plugin:activate itilflow
   php bin/console cache:clear
   ```

   После смены версии в файлах GLPI переводит плагин в состояние «требует
   обновления» и выключает его. Пока `plugin:install` не выполнен, маршрутов
   на заявках не видно. В интерфейсе это кнопка «Обновить» в списке плагинов —
   не «Удалить».
4. **`itilflow_status_sync`** — включите, как при установке.
5. **Проверка** — как при установке, плюс одна заявка по каждому рабочему
   маршруту под обычными ролями.

Миграция накопительная: обновление с более ранних 1.x идёт тем же путём,
но проверялось обновление именно с 1.7.0.

### Что меняется для существующих маршрутов

- **Порядок исходов не меняется.** Все маршруты остаются в прежнем порядке;
  на новый каждый переводится кнопкой «Перевести на новый порядок»
  на странице маршрута, и он действует только на новые запуски.
- **Полномочия проверяются строже — во всех режимах контроля.**
  «Завершить» и «Пропустить» больше не закрывают этап-согласование и этап
  с дочерней заявкой: их закрывает ответ согласующего и решение (исход)
  дочерней заявки. Согласование без назначенного согласующего ждёт назначения,
  а не открывается всем исполнителям. Режим «Журнал» больше не пропускает
  действия без полномочий — только нарушения порядка.
- **Принудительное завершение** требует права «Обход маршрута»
  (для задачи и согласования — либо права изменения «Маршрутов этапов»)
  и причины; пишется в журнал отдельной записью.
- **Отзыв заявки инициатором** у маршрутов, запущенных до обновления,
  недоступен: исходный инициатор старых запусков не сохранялся, и плагин
  не угадывает его по текущим участникам заявки.
- **Пороги идущих согласований** закрепляются при обновлении такими, какими
  они были в настройке этапа.
- **Вкладка маршрута** на заявке выглядит иначе: одна таблица этапов.

### Откат

Возврат прежних файлов **не откатывает схему базы**: новые поля и таблицы
останутся, а данные, записанные 1.8.0, прежняя версия не поймёт. Откат —
только восстановлением дампа базы и каталога плагина, сделанных на шаге 1.

## Удаление

**Настройки → Плагины** → «Выключить», затем «Удалить» (или
`plugin:deactivate` и `plugin:uninstall`).

Удаление снимает права плагина. Таблицы маршрутов и этапов
переименовываются в `*_backup_<дата>`, таблицы истории прохождения
остаются: история заявок не теряется вместе с плагином.
