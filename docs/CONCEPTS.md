# Понятия

**[English](CONCEPTS.en.md)** · Русский

## Маршрут, этап, запуск, попытка

| Понятие | Что это | Где видно |
|---|---|---|
| **Маршрут** | определение процесса: тип объекта, организация, контроль порядка, порядок исходов, флаги для заявителя | Администрирование → Маршруты этапов |
| **Этап** | один шаг регламента: кто делает, в каком режиме, где, с каким сроком и отчётом | вкладка «Этапы» маршрута |
| **Запуск** | маршрут, запущенный на конкретной заявке (изменении, проблеме) | вкладка «Маршрут этапов» заявки |
| **Шаг** | прохождение одного этапа в одном запуске: кто, когда, что сделано, сколько заняло | строка этапа на вкладке, лист согласования |
| **Попытка** | (новый порядок) один проход по этапам; после уточнения начинается следующая попытка в той же заявке | метка «попытка N», «История этапа» |
| **Исход** | (новый порядок) результат этапа: «Выполнено», «Отказ» или «Возврат на уточнение», с публичным текстом для заявителя | столбец «Итог» |

Номера этапов («Порядок», в «Дополнительно» формы этапа) идут с шагом 10:
новый этап получает следующий десяток сам, а этап между 10 и 20 можно
поставить номером 15 без перенумерации остальных. Два этапа с одинаковым
номером плагин не допускает — второй сдвигается в конец с предупреждением.

**Главное правило.** Объект этапа создаётся в момент входа в этап. Будущих
этапов физически нет, поэтому отметить их выполненными нечем — порядок держится
на устройстве данных.

## Режимы этапа

| Режим | Что создаётся | Когда применять |
|---|---|---|
| **Задача в заявке** | задача с группой или сотрудником внутри той же заявки; на время этапа группа добавляется в исполнители заявки | работа внутри одного отдела; итоговый ответ заявителю |
| **Дочерняя заявка** | отдельная заявка в целевой организации, связанная с исходной как дочерняя | этап уходит в другое подразделение; нужен свой SLA и своя видимость |
| **Согласование** | штатный запрос на согласование GLPI в исходной заявке | виза руководителя, владельца ресурса, бюджета |

Как этап завершается:

| Режим | Прежний порядок | Новый порядок |
|---|---|---|
| Задача в заявке | ответственный: **Ответ → Завершить этап** (или «Завершить этап» в строке этапа); отметка задачи «Выполнено», если отчёт не обязателен | так же |
| Дочерняя заявка | решение дочерней заявки | исход отдела: **«Отметить результат» → Выполнено / Отказ / Вернуть на уточнение**, либо адресное согласование в дочерней заявке; дочерняя заявка решается сама тем же текстом |
| Согласование | ответ согласующего: «Одобрить» / «Отклонить» | ответ согласующего; ответ сразу становится публичным результатом этапа |

Общие «Завершить» и «Пропустить» не закрывают согласование и дочернюю
заявку ни в каком порядке. Закрыть такой этап без ответа можно только
принудительно, с правом и причиной (см. [RIGHTS.md](RIGHTS.md)).

### Кто согласует

Поле этапа **«Кто согласует»**:

- **Указан в этапе** — согласующий известен заранее: согласующая группа или
  согласующий сотрудник.
- **Выбирают при прохождении** — этап открывается и ждёт, пока
  исполнитель заявки или администратор процессов укажет согласующих
  и основание выбора («Почему он»). Пункт «Указать согласующего» есть в строке
  этапа и в меню **Ответ** ленты заявки.

Согласующих можно указать **несколько** — каждому уйдёт своя виза. Сколько виз
нужно, задаёт **«Сколько виз нужно, %»** в «Дополнительно»: 100 — нужны все,
50 — половина.
Отказ отклоняет этап, как только порог становится недостижим. Подменить
согласующего после создания виз нельзя. Кто указал, кого и почему, видно
в ленте заявки и в листе согласования.

Отдельного права профиля согласующему не нужно: GLPI 11 показывает кнопки
ответа тому, кто назначен согласующим (с учётом групп и замещения).

## Два порядка исходов

| | Прежний порядок | Новый порядок |
|---|---|---|
| Исход дочерней заявки | её решение | явный ответ исполнителя или визы в ней; статус дочерней заявки сам по себе не исход |
| Отказ | «При отказе»: остановить, вернуться на этап, прервать | «Что делать при отказе»: ответить заявителю отказом и завершить маршрут или остановить маршрут; возврат — отдельным действием «Вернуть на уточнение» |
| Уточнение у заявителя | нет | возврат к разрешённой точке, ожидание ответа, новая попытка |
| Конец маршрута | снимается запрет решения; решение оформляет исполнитель | заявка решается автоматически с итогом |
| Статус заявки по этапу | ставится сразу при открытии этапа | ставит автоматическое действие `itilflow_status_sync` |
| Определение | номер версии растёт, но идущие заявки читают текущую настройку этапов | полный снимок определения закрепляется при запуске |

С 1.9.0 **новый маршрут сразу работает по новому порядку** — выбора в форме
нет. Прежний порядок остаётся у маршрутов, заведённых раньше, и у маршрутов,
созданных через API без поля `outcome_contract`.

Старый маршрут показывает плашку и кнопку **«Перевести на новый порядок»**.
Перевод заполняет пустые поля этапов из прежних: «прервать» → «ответить
заявителю отказом», «остановить» → «остановить», «вернуться на этап N» →
«остановить» и точка возврата N, у дочерних заявок — «исполнитель отмечает
результат», у задач — «остановить» без точек возврата. Подготовленное
заранее не меняется. Всё — одним сохранением, версия маршрута растёт на один.
Начатые заявки доходят по прежнему порядку, новые идут по новому.
Обратного перевода в форме нет; через API значение по-прежнему меняется.

В форме этапа видны поля только порядка маршрута: у старого — «При отказе»
и «Вернуть на этап», у нового — «Как отдел сообщает итог», «Что делать при
отказе» и точки возврата.

## Исходы, отказ, уточнение (новый порядок)

### Исход отдела

У этапа «Дочерняя заявка» поле **«Как отдел сообщает итог»**:

- **Исполнитель отмечает результат** — исполнитель дочерней заявки
  (лично или через группу) нажимает «Отметить результат» и пишет результат,
  который увидит заявитель. Внутренний комментарий — по желанию. Так —
  по умолчанию у нового этапа.
- **Визой в заявке отдела** — в дочерней заявке создаются визы ответственным
  этапа (группе и/или сотруднику), исход определяют их ответы по «Сколько виз
  нужно».

Решить дочернюю заявку вручную, не отметив исход, нельзя: GLPI покажет,
что исход отмечается на вкладке маршрута. После исхода дочерняя заявка
решается сама тем же текстом.

### Отказ

Поле **«Что делать при отказе»** (блок «Если отказ» у дочерней заявки
и согласования):

- **Ответить заявителю отказом и завершить маршрут** — маршрут заканчивается,
  заявка решается с текстом «Отказ на этапе „…“» и причиной. Так —
  по умолчанию у нового этапа.
- **Остановить маршрут** — маршрут встаёт; администратор процессов решает,
  что дальше: новая попытка с разрешённой точки или прерывание маршрута.

У задачи в заявке отказа не бывает: поля в форме нет, значение «остановить»
плагин ставит сам.

Неотвеченные визы текущего этапа при отказе, возврате, отзыве и прерывании
снимаются, чтобы не висеть у согласующих.

### Возврат на уточнение и новая попытка

Поле **«Куда можно вернуть на уточнение»** — галочки «этот этап
и предыдущие», с номерами: с каких этапов можно продолжить после уточнения.
У нового этапа «этот этап» отмечен сразу, номер подставляется при сохранении.
У задачи то же поле называется «Новая попытка после завершения» и лежит
в «Дополнительно». Удалённый этап сам убирается из точек возврата других
этапов — с сообщением.

1. Исполнитель отдела или согласующий выбирает **«Вернуть на уточнение»**
   и пишет, что уточнить у заявителя.
2. Маршрут ждёт: заявитель видит «Ответьте, пожалуйста, комментарием в этой
   заявке» и отвечает обычным комментарием.
3. Исполнитель основной заявки или администратор процессов нажимает
   **«Продолжить после уточнения»**, кратко пишет, что уточнено, и выбирает
   этап, с которого продолжить.
4. Начинается новая попытка в той же заявке. Прежние исходы и визы остаются
   в «Истории этапа».

После отказа, прерывания или завершения новую попытку может начать
администратор процессов из меню строки («Новая попытка…»). Решённую или
закрытую заявку сначала нужно открыть штатным способом GLPI.

## Итог заявителю

**Новый порядок.** Когда пройден последний этап, заявка решается автоматически:

> Заявка выполнена: все этапы маршрута «…» пройдены.
> Итог: <результат последнего этапа>

Итог — публичный результат последнего отдела или визы. Если маршрут кончается
этапом «Задача в заявке» (например «Итог заявителю») и ход этапов пишется
в ленту, в итог идёт отчёт этого этапа. Отказ с «Ответить заявителю отказом и завершить маршрут»
и отзыв заявителем тоже завершаются решением с причиной; открытая работа
отдела при этом решается с пометкой, что она больше не нужна.
Прерывание маршрута администратором пишет причину в ленту заявки, решение
заявки после этого оформляется штатно.

Принять или отклонить решение — по правилам GLPI, за заявителем.
Автоматического закрытия плагин не делает.

**Прежний порядок.** После последнего этапа снимается запрет решения,
и решение оформляет исполнитель заявки.

## Статус заявки по этапам

Поле этапа **«Статус заявки на этапе»** (в «Дополнительно»): какой статус
получает заявка, когда этап начинается. Для нового этапа подставляется
по режиму: согласование — «Согласование», дочерняя заявка — «Ожидание»,
задача — «В работе (назначена)». «Не менять» — плагин статус не трогает (сам
GLPI может сменить его по своим правилам). Завершающих статусов в списке нет:
решение — дело всего маршрута.

- Прежний порядок — статус ставится сразу при открытии этапа.
- Новый порядок — запрос статуса ставится в очередь, её разбирает
  автоматическое действие `itilflow_status_sync` (раз в минуту, нужен системный
  cron). Пока статус не подтверждён, учитывается фактический статус заявки.
  Ошибка смены статуса видна администратору и не создаёт второй этап; повтор —
  пунктом «Повторить смену статуса».

## Контроль порядка

Плагин работает на двух уровнях GLPI: отзывает право на объекты чужого или
ещё не открытого этапа (форма, Kanban, массовые действия, API) и отменяет
изменение объекта внутри сохранения, если оно нарушает порядок.

Поле маршрута **«Если действуют не в свой этап»** (в «Дополнительно»)
определяет, что делать с нарушением порядка:

| Режим | Поведение |
|---|---|
| **Журнал — разрешить и записать** | действие проходит, нарушение записывается |
| **Предупреждение — разрешить с предупреждением** | действие проходит с предупреждением, нарушение записывается |
| **Запрет — не дать сделать** | действие отменяется с объяснением |

Режим касается только порядка. Полномочия — доступ к заявке и организации,
текущий исполнитель, адресат визы — проверяются всегда, в любом режиме.
Записи видит администратор процессов в блоке «Действия вне порядка этапов»
под таблицей маршрута.

**«Решить заявку — только после всех этапов»** — пока маршрут не пройден,
заявку нельзя решить и нельзя добавить решение.

## Организации

Поле этапа «Дочерняя заявка» **«Где создать заявку отдела»**:

- **В организации основной заявки** — заявка отдела там же, где заявка.
- **В указанной организации** — всегда в выбранной (централизованная служба).
- **В организации группы** — по группе.

Группа отдела должна быть видна в этой организации. GLPI позволяет
назначить группу чужой организации без ошибки, и заявка зависает у группы,
которая её не видит. Плагин это проверяет и останавливает маршрут
с сообщением вместо создания «мёртвой» заявки, а строка готовности
предупреждает заранее: «группа … не видна в организации …».

## Сроки

- **Срок этапа** — в рабочих днях или рабочих часах календаря маршрута.
  Рабочий день — среднее число рабочих часов на рабочий день календаря:
  у «8:00–17:00, пять дней» это 9 ч; без календаря — 24 ч. В базе срок
  по-прежнему хранится в минутах; значение, которое не записать днями или
  часами, показывается в минутах. Просрочку отмечает `itilflow_deadlines`:
  помечает шаг, пишет личный комментарий, делает запись в журнал. Работу
  не блокирует. Смена календаря маршрута меняет показ в днях, но не срок
  в минутах.
- **SLA заявки отдела** (в «Дополнительно» дочерней заявки) — штатный срок
  с обратным отсчётом и календарём. У задачи своего SLA в GLPI нет.
- **Плановая продолжительность задачи** (в «Дополнительно» задачи) —
  трудоёмкость для учёта, а не срок.

Независимо от режима плагин записывает фактическую длительность каждого шага.

## Строка готовности

Над формой маршрута и над таблицей этапов — строка готовности: «Готов
к запуску · N этапов · запускает правило «…»» или «Не готов к запуску — не
хватает: K» со списком. Проверки те же, что плагин делает при запуске,
и ещё три: маршрут выключен, правило запуска не видит маршрут, группа
отдела не видна в организации. У строки про этап — ссылка на этап, на самой
форме этапа — его недостающее. Если выключено автоматическое действие смены
статуса, администратор GLPI видит служебную строку с его именем, остальные —
«сообщите администратору GLPI». Строка ничего не записывает.

## Вкладка маршрута на заявке

Одна таблица: № · Этап (с меткой режима) · Ответственные · Итог · Срок.

- **Итог** — метка состояния («Сейчас», «Впереди», «Выполнено», «Отказ»,
  «Возврат на уточнение», «Ждём уточнения», «Пропущен», «Отозвано»,
  «Прервано», «Не выполнялся»), строка результата и автор. Прежние попытки
  свёрнуты в «Историю этапа».
- **Действие** — кнопка в строке текущего этапа, форма раскрывается под строкой:
  «Завершить этап», «Отметить результат», «Согласовать или отказать»,
  «Указать согласующего», «Продолжить после уточнения», «Пояснить заявителю».
  Кнопку видит только тот, кто может выполнить действие.
- **Меню строки «…»** — «Передать этап…», «Закрыть принудительно…»,
  «Новая попытка…», «Повторить смену статуса», «Сверить ответ согласующего».
- **Шапка** — «Лист согласования», «Прервать маршрут…», «Возобновить маршрут».
- **Заявитель** в самообслуживании видит упрощённую таблицу (если включено
  «Вкладка маршрута у заявителя») и кнопку «Отозвать заявку»
  (если включено «Заявитель может отозвать заявку»).
- **Дочерняя заявка отдела** показывает строку своего этапа с формой исхода.

На телефоне таблица складывается в карточки.

## Лист согласования и отчёт

- **Лист согласования** — печатная сводка прохождения: по каждому шагу
  ответственный, передача с причиной, кто закрыл, начало, срок, окончание,
  длительность, просрочка, результат и отчёт.
- **Отчёт по узким местам** — **Администрирование → Маршруты этапов → Узкие
  места**: по этапам прохождения, средняя, медиана и максимум длительности,
  просрочки, возвраты, передачи. Затор там, где максимум сильно больше медианы.

## Версия определения

Каждое сохранение маршрута и его этапов увеличивает номер версии
(«Версия» в «Дополнительно» формы маршрута). В прежнем порядке номер
версии — не снимок: идущие заявки читают текущую настройку этапов, поэтому
существенно изменённый порядок лучше оформлять отдельным маршрутом, а старый
сохранять до завершения его заявок. В новом порядке полный снимок
определения закрепляется при запуске и правками не подменяется.
